# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A Warhammer 40k (11th edition, 2026 refresh) army-management app: **Roster Builder + Battle Tracker + dice Simulator**, backed by real unit data mirrored from the community BSData project rather than hand-entered. It is a proof-of-concept — the plumbing is proven end-to-end; the UI is deliberately plain.

Three layers, each in its own tree:
- `tools/` — offline data pipelines that produce static JSON reference data (run rarely, not part of the request path).
- `backend/` — FastAPI + SQLite API (rosters, units, battles, and the simulator).
- `frontend/` — React + Vite + TypeScript UI calling that API.

## Environment

- Windows, PowerShell. The Python interpreter is the repo-root venv: **`.venv/Scripts/python.exe`** (there is no separate backend venv). Commands below assume you `cd` into a subdir and reach it as `../.venv/Scripts/python.exe`.
- One-time setup: `.venv/Scripts/python.exe -m pip install -e "backend[dev]"` then `cd frontend && npm install`.

## Architecture

### Reference-data pipeline (offline → static JSON → served/imported)

Unit stats/weapons/abilities and missions are **not authored in this repo** — they're generated by the tools and committed as JSON, then either imported into the DB or served straight off disk:

- **`tools/bsdata-indexer/`** fetches BSData's JSON mirror of GW's BattleScribe catalogues, resolves each unit's `entryLink` for keywords/stats/abilities/weapons, and cross-references points against the Munitorum Field Manual (**MFM is the authoritative points source**; catalogue points can be stale). Output: `tools/bsdata-indexer/output/<faction>.json` (+ `army-rules.json`). Units with no MFM match are still emitted (`mfm_matched: false`), never dropped — gaps stay visible. Name matching is deliberately case-insensitive (MFM title-cases; catalogues use sentence case).
- **`tools/gdmissions/`** fetches 11th-edition mission/layout data → `tools/gdmissions/output/*.json`.
- **`scripts/import_unit_definitions.py`** loads the indexer output into the `UnitDefinition` table (upsert). The mission/army-rules/detachments routers instead read their JSON straight off disk each request — regenerate the tool output and the next request picks it up (no import step, no DB table).

### Backend (`backend/app/`)

FastAPI + SQLModel over SQLite (`backend/warhammer.db`; override with `WARHAMMER_DB_PATH` for a throwaway/test DB). Everything (rosters, units, attachments, synergies, pools, in-progress battles) is written to the DB on every change — nothing lives only in memory.

Key design ideas that span files:

- **`UnitDefinition` is read-only reference data** (id = the indexer's `source_entry_id`), created only by the import script. `Roster`/`Unit`/etc. are the user's own editable data. `Unit.loadout` and `Unit.model_groups` are populated **only** by roster import (from a BattleScribe/NewRecruit export via `battlescribe_import.py`); manually-added units get `[]` and fall back to showing `UnitDefinition.weapons` as reference.
- **The battle engine derives, rather than stores, transient state.** `BattleSession.global_step` is a single monotonic int, bumped once per `PATCH /battles/{id}/advance-phase`. `current_phase`, `active_player`, `battle_round`, and the transition type all derive from it (`app/phases.py`) so they can't drift. Likewise `ActiveEffect.expired` and `PlayerState.vp` are **computed at read time**, never auto-persisted/auto-deleted.
- **"Surface consequences, don't enforce them."** The tracker warns (e.g. `eligibility_warning`: Advanced → can't shoot) but never blocks the action; effect dismissal is always an explicit user delete.
- **Mission text is never denormalized** — a battle stores only the two dispositions and re-derives the resolved missions/layout from the gdmissions JSON every time.

### The Simulator — the one real "rules engine" (`backend/app/sim/`)

Everything else in the app is intentionally **bookkeeping, not a rules engine** (see the comment in `frontend/src/weapons.ts` — its `parseAttacks` *averages* dice for charts). The simulator is the deliberate exception and is walled off in its own package. Keep that boundary: don't tangle sim logic into the bookkeeping/averaging code.

- Pure, dependency-free Monte Carlo of the 11th-ed attack sequence: `dice.py` (rolls dice notation with an injectable `random.Random`), `keywords.py` (parses the weapon `Keywords` string into typed flags), `profiles.py` (typed attacker/defender from the raw string-dicts), `sequence.py` (one volley: hit → wound → save → damage, with **no damage spillover** — excess damage on a slain model is lost), `montecarlo.py` (N trials → wounds-dealt + models-slain distributions). `weapon_count` fires a whole squad against one shared target per trial.
- `abilities.py` is a **heuristic** extractor that pulls attack modifiers (+1/−1 Hit/Wound, re-rolls, Feel No Pain) out of a unit's free-text abilities so the UI can offer them as conditional toggles. It is explicitly *not authoritative*: the UI always shows raw ability text and keeps manual controls, so a miss is never silently applied.
- `POST /simulate` (stateless: takes raw characteristic/stat dicts, not DB ids) and `POST /simulate/analyze` (returns detected ability toggles) are in `routers/simulate.py`, which logs each request/result under the `app.simulate` logger (`main.py` calls `logging.basicConfig` so those show in the console).

### Frontend (`frontend/src/`)

React + Vite + TS; one notable dep is `recharts` (Army Analysis + simulator charts). `api.ts` is the single API client — `BASE_URL` is derived from `window.location.hostname:8000`, so localhost and LAN both work with no config. Pages are in `pages/`, routed in `App.tsx`. `weapons.ts`/`units.ts` do the client-side Army Analysis math (averaging, bucketing) — this is bookkeeping, kept separate from the backend simulator.

## Gotchas / conventions

- **Copyright**: unit stats/points/rules text are GW's copyrighted content mirrored by BSData — see `tools/bsdata-indexer/README.md`'s license caveat before this leaves private/reference use. The GW rulebook PDFs under `docs/rules/` are **gitignored on purpose** (`docs/rules/*.pdf`) — kept locally, never committed/pushed.
- Match the surrounding style: backend uses `from __future__ import annotations`, dataclasses, and terse explanatory docstrings (see `app/models.py`); the comments explain *why*, not *what*.
- The active branch is `feature-poc`; `main` is the default. Commit/push only when asked.

## Model Routing & Delegation Policy

- **Core Reasoning (Opus)**: Use Opus exclusively for high-level architecture, complex debugging, security analysis, and step-by-step planning.
- **Execution & Implementation (Sonnet)**: Delegate all code authoring, mechanical refactoring, and command execution tasks to a Sonnet sub-agent via the Task tool (`model: "sonnet"`) or rely on the built-in `/model opusplan` workflow.
- **Sub-Agent Limits**: Never spawn more than 3 parallel sub-agents at once to prevent context window bloat and runaway token consumption.
